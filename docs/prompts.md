# Как фабрика разговаривает с моделями

Документ для разработчика, который будет это править. Описывает, из чего складывается каждый запрос
к модели, кто что решает, и где это менять.

Соседние документы: `docs/content-format.md` (формат, который всё это порождает), `README.md`
(как запускать).

## Три разных механизма

Слово «промпт» покрывает три непохожие вещи, и путать их дорого.

| Что | Куда ходит | Чем управляется | Сколько запросов |
|---|---|---|---|
| **Тексты страниц** | OpenAI, Responses API | `factory/prompts/texts.json` + файлы темы | ~12 на страницу |
| **Картинки страниц** | Runware | `factory/prompts/images.json` | 1 на картинку |
| **Логотип** | Runware, две модели подряд | `factory/prompts/logo.json` | 2 на сайт |

Ключи и модели — в `.env`, образец в `.env.example`. Ключ читается в объект и **никогда** не
попадает в `process.env`, в лог, в тексты ошибок и в готовый сайт.

# 1. Тексты

## Из чего состоит запрос

Каждый запрос к OpenAI собирается в `factory/texts/openai.mjs` (`askJson`) и имеет ровно три части:

```js
{
  model,                                    // из .env
  instructions,                             // НЕИЗМЕННАЯ часть — одна на весь прогон
  input: [{ role: 'user', content: brief }], // ИЗМЕНЯЕМАЯ часть — своя у каждого запроса
  text: { format: { type: 'json_schema', strict: true, schema } },
  prompt_cache_key,
}
```

**Порядок обязателен.** Кеш промпта у OpenAI срабатывает только на неизменившемся начале запроса, а
`instructions` — самая большая его часть. Любая мелочь, зависящая от страницы, попавшая в
`instructions`, обнуляет кеш, и каждый следующий запрос дорожает примерно вдесятеро. Это главное
правило этого раздела; если его нарушить, ничего не сломается — просто счёт вырастет.

## Что лежит в `instructions`

Собирается один раз на прогон, в `factory/texts/plan.mjs` (`buildInstructions`), из трёх частей:

1. **Правила письма** — `factory/prompts/texts.json`, поле `rules`. Список строк: как писать, чего
   не выдумывать. Ничего про структуру страницы здесь нет и быть не должно.
2. **Описание блоков темы** — собирается кодом из `templates/<id>/blocks.json`
   (`describeBlocks` в `factory/texts/template.mjs`), не пишется руками. Выглядит так:

   ```
   - hero: between 1 and 2 text, between 0 and 1 buttons, between 0 and 1 info. its h1 and its picture are written for you
   - section: between 1 and 6 text, between 0 and 1 list, ...
   - text: 200–400 characters or items
   ```

   Поэтому новая тема получает корректный промпт сама — править промпт под каждую тему не нужно.
3. **Образцы** — все файлы `templates/<id>/examples/*.json`, целиком, как JSON.

   Образцы решают больше, чем кажется: **приём, которого в них нет, модель почти не использует.**
   Ссылка внутри абзаца, `h3`-подзаголовок, шаги — всё это модель пишет постольку, поскольку видит
   это в образце. Заводя новую тему, показывайте в образцах каждый приём, который хотите видеть.

## Четыре вида запроса

Порядок на один прогон: один кадр сайта, затем на каждую страницу план, наполнения и FAQ.

| Имя схемы | Когда | Что спрашивает | `prompt_cache_key` |
|---|---|---|---|
| `site_frame` | раз на прогон | слоган, подписи меню, футер, заголовки служебных блоков | `site-factory-site` |
| `page_plan` | раз на страницу | заголовок, описание, `h1`, имена картинок, по блокам: заголовок, о чём, куда ссылаться | `site-factory-plan` |
| `section_content` | **на каждый блок** | сам текст одного блока | `site-factory-fill` |
| `faq_answers` | раз на страницу | ответы на вопросы из плана | `site-factory-faq` |

Ключ кеша свой у каждого вида: схема входит в кешируемое начало, а схемы у них разные, так что
общий ключ всё равно не дал бы попадания.

Страница по раскладке «Длинный обзор» — это 1 план + 10 наполнений + 1 FAQ = **12 запросов**.
Маленькие запросы вместо одного большого — намеренно: длинный ответ упирается в потолок вывода
модели, и тогда теряется вся страница, а не один блок.

## Что в брифе (`input`)

Бриф — единственное место, где есть что-то про конкретную страницу. Собирается в `planPage`
(`factory/texts/plan.mjs`):

```
Brand: 899OK
Geo: Bangladesh
Language: en-US
Page: casino
Pages on this site: /, /slots, /bonus
A link to another page of this site must use one of those exact addresses.
This page is made of: 1 hero, 8 section, 1 split. It has 5–8 FAQ questions and at most 8 internal links.
Pictures on this page, in this order. Name each with a short hyphenated slug in latin
letters, such as "live-dealer-table" — never a sentence, and never in the page language,
because the name becomes a file name:
1. hero
2. split
Plan the page: a heading and a one-line brief for each section, which elements suit it and
which other pages are worth linking to. Do not write the body text yet.
```

Две вещи здесь не случайны и уже стоили живых прогонов:

- **Адреса, а не имена файлов.** Раньше модели давали `home`, `casino`, а принимались только `/`,
  `/casino` — и все ссылки выбрасывались.
- **Латиница для имён картинок.** Модель пишет на языке сайта, и имя на кириллице после очистки
  превращается в огрызок: `рулетка 2024` → `2024`. Такое имя становится именем файла и основой
  промпта и не говорит о картинке ничего.

Бриф наполнения (`fillSection`) короче: бренд, язык, заголовок блока, о чём он, **список элементов
в том порядке, в каком их писать**, куда ссылаться и заголовки соседних блоков — чтобы блоки не
повторяли друг друга. Про картинку в нём не говорится ни слова: её ставит фабрика.

## Кто что решает

Это главное, что стоит понять про устройство.

| Решает фабрика | Решает модель |
|---|---|
| какие блоки на странице и в каком порядке | заголовки и текст |
| сколько блоков каждого вида | о чём каждый блок |
| какие элементы внутри блока и в каком порядке (если раскладка их назвала) | какие элементы (если не назвала) |
| где стоит картинка | как картинка называется |
| оглавление, «другие страницы», заголовки служебных блоков | вопросы FAQ и ответы |
| адреса ссылок (чинятся и проверяются после модели) | где в тексте поставить ссылку |

Всё, что решает фабрика, модель **не может сломать**: схема строгая (`strict: true`), и ответ
декодируется против неё. Число блоков и число элементов в ответе — не просьба в тексте, а
`minItems`/`maxItems`, которым ответ обязан соответствовать.

## Где что менять

| Хочу | Файл |
|---|---|
| поменять тон, запреты, что не выдумывать | `factory/prompts/texts.json` → `rules` |
| поменять, что блок может держать и сколько | `templates/<id>/blocks.json` → `blocks.<тип>.content` |
| поменять длины текста, бюджеты ссылок | `templates/<id>/blocks.json` → `lengths`, `links` |
| поменять состав страницы, порядок блоков, точную последовательность элементов | `layouts/*.json` |
| показать модели приём, который она не использует | `templates/<id>/examples/*.json` |
| поменять модель или цены | `.env` |
| поменять текст самого брифа | `factory/texts/plan.mjs`, `fill.mjs`, `site-json.mjs` |

Первые пять — это данные, код трогать не нужно. Последние два — код.

# 2. Картинки страниц

Совсем другая история, и здесь есть **существенная оговорка**.

Как это работает (`factory/images/generate.mjs`, `prompts.mjs`):

1. Фабрика собирает имена картинок со страниц сайта — те самые ярлыки, которые придумала модель
   текстов (`slot-reels`, `live-dealer-table`).
2. Для каждой, которой ещё нет в `images.json`, берётся промпт **случайно из списка** в
   `factory/prompts/images.json`, без повторов, пока список не кончится.
3. `{brand}` в промпте заменяется на название бренда.
4. Запрос уходит в Runware: промпт, `negativePrompt`, размер, модель из `.env`.

**Промпт не связан с именем картинки.** Картинка, названная `slot-reels`, может быть нарисована по
промпту «a cricket stadium at night». Имя уходит только в имя файла и в `alt`. Список промптов —
это набор «картинок вообще для такой тематики», а не ответ на вопрос «что здесь должно быть».

Это известный пробел, намеренно оставленный за рамками предыдущей работы (см.
`docs/specs/2026-09-18-layouts-design.md`, раздел «Что не входит»). Чинится он так: передать имя
картинки — а лучше заголовок и краткое содержание блока, в котором она стоит, — в промпт. Место
картинки теперь известно заранее, так что данные для этого есть.

**Где менять:** `factory/prompts/images.json` — список промптов, `negativePrompt` (что не рисовать),
размер. Размер обязан быть от 128 до 2048 и делиться на 16, иначе Runware отвергает каждую картинку;
проверка стоит при чтении файла, один раз.

# 3. Логотип

Два запроса подряд, `factory/images/logo.mjs`:

1. **Надпись** — модель, умеющая рисовать текст (`ideogram:4@0` по умолчанию). Промпт берётся
   случайно из `factory/prompts/logo.json`, `{brand}` заменяется на бренд. Все промпты там кончаются
   на «isolated on a plain white background» — фон потом вырезается. ~$0.06.
2. **Вырезание фона** — вторая модель (`ideogram:remove-background@0`). ~$0.01.

Дальше `sharp` обрезает поля и делает две картинки: `logo` для шапки и `logo-square` на градиенте —
для превью ссылки, иконки сайта и разметки schema.org.

Одна особенность, найденная платным прогоном и стоящая того, чтобы её знать: **вырезание фона
просит картинку по адресу, а не по идентификатору.** Runware возвращает для надписи настоящий
UUID v4 — и модель вырезания его же не принимает, отвечая «Invalid value for `inputImage`». Та же
картинка по адресу проходит. Адрес спрашивается первым, идентификатор остаётся запасным, потому что
модель вырезания — строка в `.env`, и другая может вести себя наоборот. Что именно не приняли,
пишется в лог.

**Где менять:** `factory/prompts/logo.json` — восемь стилей надписи, размер, градиенты для квадрата.
Ideogram 4.0 работает только на 2048×2048 и не принимает `negativePrompt` вовсе — файл с ним
отвергается при чтении.

# Что стоит знать про деньги

- OpenAI **не возвращает стоимость**. Она считается умножением счётчиков токенов на цены из `.env`
  (`OPENAI_PRICE_*`, доллары за миллион). Меняете модель — поменяйте и цены, иначе лог будет врать.
- Кеш промпта делает ~12 запросов на страницу посильными: повторное чтение кешированного начала
  стоит в десять раз дешевле. Отсюда правило «статика в `instructions`, динамика в `input`».
- Всё, что можно отвергнуть бесплатно, отвергается **до первого платного запроса**: сломанная
  раскладка, блок, которого тема не умеет, элемент, которого у блока нет, число вне диапазона.
- Ошибка ключа или пустой счёт останавливают весь прогон, а не перебирают страницы по одной.
- Ничего на диске не перезаписывается: повторный запуск той же папки пропускает уже написанные
  страницы и уже существующие картинки и не платит за них заново.

# Чего в этих запросах нет

Честный список того, что разработчик может искать и не найти:

- **Связи промпта картинки с тем, что на ней должно быть** — см. раздел 2.
- **Порядка элементов внутри блока, когда раскладка его не назвала.** Модель пишет их в том порядке,
  в каком видит в образцах, но гарантии нет. Гарантия есть только у `elements` в раскладке.
- **Одновременных запросов.** Всё идёт по одному; параллельность убрана намеренно и осталась
  отдельной задачей.
- **Проверки формы запроса против живого API.** Все тесты отвечают подделками, поэтому неверно
  названное поле живёт до первого платного прогона. Так уже случалось дважды.
