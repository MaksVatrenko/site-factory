# Генерация текстов через OpenAI

Как фабрика делает папку нового сайта: тексты страниц, `site.json` и метки картинок —
по выбранному шаблону, бренду, гео и языку.

Соседние документы: `docs/content-format.md` (формат, который мы порождаем),
`docs/specs/2026-09-15-image-generation-design.md` и
`docs/specs/2026-09-15-logo-generation-design.md` (этапы, которые идут после).

## 1. Что и зачем

Сегодня контент приходит от заказчика таблицей, и `npm run import:sheet` раскладывает её по
JSON-файлам. Это единственный источник страниц.

Добавляем второй: **фабрика сама пишет сайт целиком**. На входе — шаблон, бренд, гео, язык и
список страниц. На выходе — папка в `data/sites/`, неотличимая по устройству от собранной из
таблицы.

Из этого следует главное ограничение проекта: **ничего, кроме новой папки, этот этап не
производит**. Логотип, картинки и сборка работают дальше как есть и об этом этапе не знают.

Генерация текстов — отдельная операция, а не часть сборки. Она долгая, стоит денег, и результат
хочется посмотреть до сборки. Родственник здесь `import:sheet`, а не `prepare`.

## 2. Ключ и настройки

Ключ OpenAI лежит в том же `.env`, что и ключ Runware, и по тем же правилам: файл не попадает ни в
git, ни в собранный сайт; значения читаются в обычный объект и **никогда не кладутся в
`process.env`**, поэтому сборка физически не может их увидеть.

```
OPENAI_API_KEY=
OPENAI_API_URL=https://api.openai.com/v1/responses
OPENAI_MODEL=gpt-5.6-luna
# Цены в долларах за миллион токенов — под ту модель, что выбрана выше.
OPENAI_PRICE_INPUT=0.20
OPENAI_PRICE_CACHED_INPUT=0.02
OPENAI_PRICE_OUTPUT=1.20
```

| Переменная | По умолчанию | Что это |
|---|---|---|
| `OPENAI_API_KEY` | пусто | Без него этап сообщает, что пропущен, и ничего не делает |
| `OPENAI_API_URL` | `https://api.openai.com/v1/responses` | Responses API — OpenAI рекомендует его для нового кода |
| `OPENAI_MODEL` | `gpt-5.6-luna` | Меняется без правки кода: см. раздел 13 |
| `OPENAI_PRICE_INPUT` | `0.20` | Доллары за миллион входных токенов |
| `OPENAI_PRICE_CACHED_INPUT` | `0.02` | То же для токенов, прочитанных из кеша |
| `OPENAI_PRICE_OUTPUT` | `1.20` | То же для выходных токенов |

Ключ вычищается из любого текста ошибки перед тем, как попасть в лог, — как в
`factory/images/runware.mjs`. Ключ, в котором есть пробел, перенос строки или не-ASCII, считается
незаданным: заголовок `Authorization` с таким значением и есть то, из-за чего сырая ошибка `fetch`
однажды утекла с ключом внутри.

## 3. Шаблон описывает себя

**Источник структуры — шаблон, а не сайт-образец.** Шаблонов со временем будет несколько, и
страницы, написанные под один, не годятся как образец для другого.

Каждый шаблон описывает себя тремя файлами:

| Файл | Что в нём | Статус |
|---|---|---|
| `templates/<id>/manifest.json` | `blocks` и `elements` — словарь шаблона | уже есть |
| `templates/<id>/content.json` | правила каркаса: порядок блоков, сколько их, что внутри, длины | новый |
| `templates/<id>/examples/*.json` | одна-две готовые страницы в этом шаблоне | новый |

Для `review` примеры берутся из `data/sites/899ok` — они под него и написаны.

`templates/review/content.json`:

```jsonc
{
  "blocks": [
    { "type": "hero",    "content": { "title": 1, "text": [1, 2], "image": [0, 1] } },
    { "type": "toc",     "auto": true },
    { "type": "section", "count": [8, 10],
      "content": { "title": [1, 2], "text": [2, 6], "list": [0, 1], "table": [0, 1], "cards": [0, 1], "image": [0, 1] } },
    { "type": "links",   "auto": true },
    { "type": "faq",     "content": { "title": 1, "toggle": [5, 8] } }
  ],
  "images": [0, 3],
  "lengths": {
    "title": 60, "description": [120, 160], "h1": 60,
    "text": [200, 400], "listItems": [3, 8], "tableRows": [3, 10], "cards": [2, 4]
  },
  "home": { "sectionsBonus": 2 }
}
```

- Число — точное количество. Пара `[a, b]` — диапазон, в котором фабрика разыгрывает.
- `auto: true` — блок заполняет фабрика, модель к нему не прикасается.
- `images` — сколько картинок может быть на странице всего, считая картинку в `hero`.
- `home.sectionsBonus` — главная делается объёмнее прочих.

**Промпт собирается из `content.json`, а не пишется руками.** Один файл и разыгрывает каркас, и
порождает текст правил для модели, поэтому разойтись они не могут. Новый шаблон получает
корректный промпт сам, как только рядом лягут `content.json` и примеры.

Шаблон без `content.json` генерацию текстов не поддерживает: этап отказывается с понятным
сообщением. Собираться такой шаблон продолжает как обычно.

## 4. Общий файл правил

`factory/prompts/texts.json` держит то, что от шаблона не зависит:

```jsonc
{
  "rules": [
    "Write clear, useful, reader-focused content.",
    "Do not copy text from the examples — write completely new content.",
    "Do not mention competitors, rankings, search results or the research.",
    "Do not invent payment methods, licences, bonus amounts, withdrawal times, ratings, reviews or legal claims that are not in the examples.",
    "Avoid unsupported first-person experience, fabricated testimonials and absolute promises.",
    "Keep the meta title and description accurate and natural, without keyword stuffing."
  ]
}
```

Правила редактируются как `logo.json` и `images.json` — без правки кода.

### Таблица гео → язык

Живёт отдельно, в `factory/geos.json` — это справочник, а не правило письма, и его же читает
`GET /api/geos`, чтобы наполнить выпадающие списки «Гео»/«Язык» в форме:

```jsonc
{
  "Bangladesh": "en-US", "Philippines": "en-US", "Pakistan": "en-US", "India": "en-IN",
  "Indonesia": "id-ID", "Mexico": "es-MX", "Brazil": "pt-BR"
}
```

Порядок строк — это порядок в выпадающем списке «Гео», поэтому файл не сортируется нигде в коде:
частые гео можно держать сверху. **Новая страна добавляется одной строкой в `factory/geos.json`**,
без правки кода; `factory/geos.mjs` читает файл и по нему же строит список стран и список
различающихся языков. Битый или нечитаемый файл не роняет форму: `GET /api/geos` в этом случае
отвечает пустыми списками, а `factory/texts/generate-site.mjs` — тем же логом «пропущено», что и у
шаблона без `content.json`.

### Чего в промпте не будет

Половина исходного промпта, с которого начинался проект, — это уговоры выдать валидный JSON.
Строгая схема и сборка на стороне фабрики делают их лишними:

| Правило из исходного промпта | Чем заменено |
|---|---|
| `Return valid JSON only` | Строгая схема: невалидный JSON невозможен |
| `Close every array and object` | То же |
| `Do not truncate the response` | Обрыв определяется по признаку в ответе и повторяется точечно |
| `Follow the JSON structure of the examples` | Схема + сборка на фабрике |
| `Preserve the same section count, order and types` | Каркас разыгрывает фабрика до запроса |

Остаются только правила про смысл и тон — то, что схемой не выразишь.

## 5. Что задаёт человек

Новая вкладка «Тексты» (сейчас там заглушка):

| Поле | Что это |
|---|---|
| Шаблон | Из списка шаблонов; нужен `content.json` |
| Папка | Имя новой папки в `data/sites/`. Существующая не перезаписывается |
| Бренд | Название бренда |
| Гео | Страна. Выпадающий список из `factory/geos.json` (раздел 4) |
| Язык | Тоже выпадающий список оттуда же. Пустое значение подставляется из гео при его выборе, дальше правится руками |
| Страницы | Текстовое поле, по странице на строку, заполнено набором по умолчанию |

Список страниц — обычные имена файлов без расширения: `home`, `casino`, `slots`, `bonus`. Имя
становится адресом и задаёт тему страницы. `home` обязателен: без него у сайта не будет главной.

Командой то же самое:

```bash
npm run generate:texts -- --template review --out 520bdapp \
  --brand "520BD" --geo Bangladesh --pages home,casino,slots,bonus
```

Готовая папка появляется в списке сайтов на вкладке «Генерация». Дальше всё как обычно.

## 6. Каркас

До первого запроса фабрика разыгрывает из `content.json` числа — не содержание:

- сколько секций на каждой странице;
- сколько вопросов в FAQ;
- сколько картинок на странице.

Жребий берёт зерно из имени папки, поэтому повторный запуск даёт тот же каркас. Разные сайты
получают разные каркасы — это и есть разнообразие сетки, и оно не зависит от модели.

## 7. Этап 1 — план страницы

Один запрос на страницу. Ответ маленький, меньше тысячи токенов.

Модели уходит: правила, `content.json` в виде текста, примеры страниц, бренд, гео, язык, имя
страницы, список всех страниц сайта и разыгранные бюджеты.

```jsonc
{
  "title": "…",
  "description": "…",
  "h1": "…",
  "heroText": ["…"],
  "heroImage": "roulette-table",
  "sections": [
    { "heading": "Payment methods",
      "brief": "какие способы пополнения есть и чем отличаются",
      "elements": ["text", "text", "table"],
      "image": "payment-methods",
      "links": ["/bonus"] }
  ],
  "faq": ["вопрос", "вопрос"]
}
```

`heroImage` и `image` у секций — это `null`, когда картинка не нужна. Вместе они не могут
превысить бюджет страницы из `content.json`.

**Набор элементов выбирает модель, а не жребий.** Если бы фабрика вслепую назначила секции
таблицу, а секция оказалась про ответственную игру, получилась бы таблица ни о чём. Модель видит
тему и решает сама — но выбирает строго из словаря шаблона и в пределах разыгранных бюджетов.

Фабрика проверяет план и подрезает вышедшее за рамки: лишние элементы, картинки сверх бюджета,
ссылки на несуществующие страницы. Подрезанное пишется в лог.

## 8. Этап 2 — наполнение секции

По запросу на секцию. На вход: заголовок, бриф, список элементов и **заголовки всех остальных
секций страницы**. Последнее дёшево и снимает главную болезнь посекционной генерации: модель
знает, о чём напишут соседи, и не пересказывает их.

FAQ наполняется одним запросом на все вопросы: ответы короткие.

Ответ — массив элементов нашего формата. Семь видов элементов описываются в схеме через `$defs` и
собираются через `anyOf` внутри `items`:

```jsonc
{
  "type": "object",
  "properties": {
    "items": { "type": "array", "items": { "anyOf": [
      { "$ref": "#/$defs/title" }, { "$ref": "#/$defs/text" }, { "$ref": "#/$defs/list" },
      { "$ref": "#/$defs/table" }, { "$ref": "#/$defs/cards" }, { "$ref": "#/$defs/toggle" },
      { "$ref": "#/$defs/image" }
    ] } }
  },
  "required": ["items"],
  "additionalProperties": false,
  "$defs": { }
}
```

Требования строгого режима, которые надо соблюсти в каждом `$defs`:

- `additionalProperties: false` у каждого объекта;
- **все** поля перечислены в `required`; необязательное поле выражается как «тип или `null`»
  (например `image` у карточки, `width`/`height` у картинки);
- вложенность до 10 уровней, до 5000 свойств суммарно — нам далеко до границ;
- корень схемы — объект, не `anyOf`; вложенный `anyOf` разрешён.

## 9. Сборка и проверки

Страницу собирает фабрика, а не модель.

- `hero` — `h1` и абзацы из плана;
- `toc` — **строится из заголовков секций**: по пункту на секцию, в том же порядке. Связка, которую
  модель ломала бы чаще всего, просто перестаёт существовать;
- `section` — из ответов этапа 2;
- `links` — из меню `site.json`;
- `faq` — из ответа на вопросы плана.

Проверки перед записью файла:

| Что проверяется | Что делается при нарушении |
|---|---|
| Ровно один `h1` на странице | Гарантируется схемой, а не проверкой: `h1` — единственное строковое поле плана, а свой заголовок внутри секции модель может дать только как `h3` |
| Пунктов в `toc` столько же, сколько секций | Оглавление пересобирается из секций |
| Имена картинок — только объявленные планом | Лишняя метка убирается |
| Внутренние ссылки ведут на страницы из списка | Ссылка разворачивается в обычный текст |
| Количества в пределах `content.json` (пункты списка, строки таблицы, карточки) | Лишнее отбрасывается, строка в лог |
| Длины текста в пределах `content.json` | Только строка в лог: обрезать абзац на полуслове хуже, чем оставить длинный |

Ничто из этого страницу не роняет. Это тот же принцип, что уже у движка: контент не отвергается
никогда, а всё неудавшееся перечисляется в логе.

## 10. site.json и язык

Один запрос на сайт. Модель пишет то, что видит читатель: названия пунктов меню, заголовки колонок
футера, возрастное предупреждение, слоган, копирайт — на языке сайта.

Не у модели, а из формы: `locale`, `brand.name`. Домена форма не спрашивает вовсе: в `site.json`
он всегда пишется пустой строкой. Это не страшно — при сборке сайта его перекрывает своё поле
«Домен», как и всегда, так что до итогового сайта пустая строка не доходит. Пункты меню строятся
из списка страниц: адрес берёт фабрика, название пункта пишет модель. Поэтому добавленная в список
страница появляется в шапке и футере сама.

Язык определяется полем «Язык». Если оно пустое, берётся из гео по таблице раздела 4; если гео
незнакомое — английский, со строкой в лог.

## 11. Место в фабрике

```
Тексты  →  папка в data/sites/  →  [ логотип → картинки → сборка ]
                                    существующий конвейер, без изменений
```

Повторный запуск на ту же папку **пропускает уже готовые страницы** — как этап картинок пропускает
существующие. Так прерванный прогон продолжается, а не начинается заново.

Страницы пишутся по одной, по мере готовности. Прогон, упавший на пятой странице, оставляет четыре
рабочие.

## 12. Ошибки

Этап никогда не бросает наружу: каждая беда — строка в логе.

| Случай | Что делает фабрика |
|---|---|
| Нет ключа | Сообщает и не делает ничего |
| `429`, `500`, `503` | Повтор с нарастающей паузой и разбросом; `Retry-After` соблюдается как минимум |
| Нехватка денег на счёте | Прогон останавливается сразу: повторы не помогут |
| Ответ оборван по лимиту | Определяется по признаку в ответе; не повторяется — тот же запрос упрётся в тот же потолок вывода, повтор лишь оплатит его заново |
| Модель отказалась отвечать | Секция запрашивается заново, без паузы — до 3 попыток всего; если не вышло ни разу, секция пропускается |
| Секция так и не вышла | Страница пишется без неё, строка в лог |

## 13. Деньги

**Цена не приходит в ответе.** У Runware есть `includeCost`, у OpenAI такого поля нет: ответ несёт
только счётчики токенов (`usage`), отдельно считая те входные токены, что были прочитаны из кеша.
Поэтому деньги считает фабрика — умножением счётчиков на цены из `.env`. Это делает цены
**настройкой, а не фактом**: сменили модель — поменяйте и три цены, иначе лог будет врать. Лог
показывает и токены, и деньги, по странице и итогом по сайту.

Длинный неизменный префикс (правила, `content.json`, примеры) уходит в каждый из примерно девяноста
запросов на сайт. Кеширование промпта у OpenAI включено само собой, повторное чтение префикса
стоит вдесятеро меньше. Отсюда требование к порядку запроса: **неизменное впереди, изменяемое в
конце**, иначе кеш не попадает. Схема ответа входит в префикс, поэтому у плана и у наполнения кеши
разные — это нормально, просто два первых запроса дороже.

Прикидка на сайт из восьми страниц (около 89 запросов, префикс ~8,2 тысячи токенов):

| Модель | Примерно за сайт |
|---|---|
| `gpt-5.6-luna` | $0.03 |
| `gpt-5.6-terra` | $0.33 |

Цены взяты из документации OpenAI и должны быть сверены со счётом перед первым большим прогоном.
Документация **не сравнивает модели по качеству прозы на конкретных языках** — это проверяется
только опытом, поэтому модель и вынесена в `.env`.

## 15. Тесты

Ни один тест не ходит в сеть и не видит настоящий ключ: `fetchFn` подменяется, `.env` берётся
временный — как в тестах Runware.

- **Ключ не утекает.** Ключ-метка не появляется ни в `process.env`, ни в логе, ни в одном файле
  готового сайта.
- **Схема.** Схема строится из словаря шаблона: элемент, которого шаблон не умеет, в неё не
  попадает. Ответ по схеме собирается в страницу; элемент неизвестного вида в ответе отбрасывается
  при сборке.
- **Оглавление.** Сколько бы секций ни вернула модель, пунктов в `toc` ровно столько же и в том же
  порядке.
- **Ссылки.** Ссылка на страницу не из списка разворачивается в текст.
- **Картинки.** Метка с именем, которого не было в плане, убирается.
- **Каркас воспроизводим.** Одно зерно — один каркас; разные имена папок — разные каркасы.
- **Повторный запуск.** Готовые страницы не переписываются и не оплачиваются заново.
- **Обрыв и отказ.** Обрыв по лимиту не повторяется вовсе, отказ модели повторяется до 3 попыток —
  в обоих случаях, так и не получив ответ, фабрика пишет страницу без этой секции и строку в лог.
- **Деньги считаются даже при сбое** — как в этапе логотипа.
- **Сайт собирается.** Сгенерированная папка проходит настоящую сборку Astro.

## 16. Что не входит

- Batch API со скидкой 50% — пригодится вкладке «Массовая генерация», не этому этапу.
- Показ плана человеку на утверждение до оплаты текста. Схема это позволяет, но интерфейса нет.
- Перевод существующего сайта на другой язык.
- Правка текстов в интерфейсе после генерации.
- Вторая модель для вычитки готового текста.
