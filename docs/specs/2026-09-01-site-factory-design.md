# Конвейер шаблонных сайтов — дизайн-документ

**Дата:** 2026-09-01
**Статус:** согласован, готов к планированию
**Область:** версия 0 (основная часть документа) + путь роста до полной архитектуры (раздел 10)

## 1. Контекст и цель

Есть поток однотипных SEO-сайтов (референс — https://4p4p.net/): жёсткий блочный каркас
(hero → описание → сетка карточек → колонки категорий → FAQ → футер с дисклеймерами),
уникальный контент, локаль под конкретное гео. Тексты и изображения генерируются внешней
системой на базе ChatGPT — это **вне зоны ответственности проекта**.

**Цель:** получая готовый контент в согласованном формате, выпускать сайт в интернет одной
командой, без ручной вёрстки и без участия разработчика в каждом выпуске; и сохранить
возможность править уже выпущенные сайты, в том числе массово — например, изменить
формулировку в футере сразу на всей сети.

### Что входит

- Контракт контента: JSON-схема блоков, служащая одновременно заданием генератору и правилом проверки.
- Валидация входящего контента.
- Рендер сайта из JSON в статический HTML/CSS.
- Автоматическая визуальная уникализация сайтов.
- Сборка, выкладка на хостинг, проверка работоспособности.
- Слоистая конфигурация, дающая массовые правки без обхода всех сайтов.

### Что не входит

- Генерация текстов и изображений (внешняя система).
- Закупка доменов и хостингов (заказчик).
- SEO-стратегия, семантика, линкбилдинг.
- Аналитика и трекинг (может быть добавлено позже как блок шаблона).

## 2. Принцип, определивший объём версии 0

**Упрощай инфраструктуру, не упрощай модель данных.**

Очередь задач, отдельная СУБД, внешнее хранилище медиа, несколько хостинг-провайдеров,
канареечная раскатка — это средства масштаба. Каждое добавляется позже за день-два и
ничего не ломает. Схема блоков, слоистый конфиг и детерминированная генерация темы —
это модель данных. Их упрощение сейчас означает миграцию всех конфигов и пересборку
всей сети потом.

Поэтому версия 0 режет инфраструктуру до минимума и полностью сохраняет модель данных.

## 3. Принятые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Контракт контента | Формат диктует конвейер: жёсткая JSON-схема + валидация на входе | Невалидные данные не попадают в пайплайн; всё дальше детерминировано |
| Модель раздачи | Статическая сборка на сайт (SSG) | Нулевая стоимость отдачи, отказоустойчивость, нет общего сервера на всю сеть |
| Шаблоны | Один движок + генерируемая тема и варианты секций | Разнообразие уровня «разные шаблоны» при одной кодовой базе |
| Правки | Слоистый конфиг (в версии 0 — два слоя) | Массовая правка = правка одной строки в общем слое |
| Рендер | Astro с компонентами на Vue | Нулевой JS по умолчанию, сборка 2–5 с против 20–40 с у Nuxt |
| Структура сайта | Многостраничная схема (`site → pages[] → blocks[]`) с самого начала | Фактически сайты одностраничные, но добавить страницы позже = переписать роутинг, меню, sitemap |
| Хранилище версии 0 | Файлы в git-репозитории, без СУБД | Список сайтов — это папка; история правок — история коммитов |
| Медиа версии 0 | Картинки складываются в папку сайта и уезжают на хостинг со статикой | Внешнее хранилище не нужно, пока картинки не переиспользуются между сайтами |
| Деплой версии 0 | Один провайдер — Cloudflare Pages | Бесплатная раздача статики, простой API |
| DNS версии 0 | Привязка домена вручную в панели Cloudflare | Два клика на домен; автоматизация окупается на десятках доменов |

## 4. Архитектура версии 0

Весь конвейер — одна команда:

```bash
make-site ./sites/4p4p.net.json
```

Пять шагов внутри, строго по порядку:

```
① Валидация       файл сверяется с Zod-схемой; при несоответствии — отказ с точным адресом ошибки
② Медиа           картинки скачиваются, сжимаются (sharp → webp/avif + ресайзы), кладутся в public/ сайта
③ Резолв конфига  global.json + sites/<domain>.json → итоговое описание сайта
④ Сборка          Astro: pages[].blocks.map(b => Registry[b.type]) → dist/
⑤ Выкладка        dist/ → Cloudflare Pages API → health-check → запись результата
```

Плюс два фоновых механизма, работающих внутри этих шагов:

- **Theme engine** (внутри ④): `seed = hash(domain)` → палитра, шрифтовая пара, радиусы,
  вариант раскладки каждой секции, порядок блоков, выбор варианта служебного текста.
- **Снапшот** (перед ④): итоговое описание сохраняется в `.builds/<domain>/<timestamp>.json`,
  что даёт откат простой пересборкой из старого файла.

**Ключевой инвариант, сохраняемый и в версии 0, и после роста:** рендер ничего не знает
о хостингах, доменах и хранилищах. Это чистая функция `site.json → dist/`. Следствия:
шаблон собирается локально из файла, тестируется без инфраструктуры, а любой слой вокруг
наращивается без правок рендера.

### Раскладка на диске

```
global.json                     общий слой: футер, дисклеймеры, флаги блоков
sites/<domain>.json             личный слой: контент, лого, домен, локаль
media/<domain>/                 оригиналы картинок (для пересборки)
.builds/<domain>/<ts>.json      снапшоты итоговых конфигов
template/                       Astro-проект: реестр блоков, компоненты, theme engine
cli/                            команда make-site
```

Список сайтов — это содержимое `sites/`. История правок — история git. Отдельный учёт не нужен.

## 5. Модель данных

Это неприкосновенная часть: она одинакова в версии 0 и в полной архитектуре.

### Слои конфигурации

Итоговое описание сайта не хранится целиком, а собирается при сборке:

```
global.json          общее для всей сети: футер, дисклеймеры, структура меню, флаги блоков
  ↓ перекрывается
sites/<domain>.json  уникальное: контент страниц, лого, домен, локаль
```

Слияние глубокое (deep merge), точечные переопределения адресуются путём:
`"blocks.reviews.enabled": false`.

Третий слой (пресеты ниш и языков) вставляется между ними при росте — формат слияния
при этом не меняется, поэтому добавление пресетов не требует правки существующих файлов.

### Схема контента (сокращённо)

```jsonc
{
  "external_id": "4p4p-id",           // идемпотентность: повторная отправка обновляет
  "domain": "4p4p.net",
  "locale": "id-ID",
  "brand": { "name": "4P4P", "logo": "https://…" },
  "pages": [
    {
      "slug": "/",
      "meta": { "title": "…", "description": "…" },
      "blocks": [
        { "type": "hero",     "props": { "title": "…", "subtitle": "…", "image": "…" } },
        { "type": "richtext", "props": { "heading": "…", "paragraphs": [ "…" ] } },
        { "type": "cards",    "props": { "items": [ { "title": "…", "text": "…" } ] } },
        { "type": "columns",  "props": { "items": [ … ] } },
        { "type": "faq",      "props": { "items": [ { "q": "…", "a": "…" } ] } }
      ]
    }
  ]
}
```

Реестр блоков расширяем: новый тип = новый компонент + запись в схеме и в реестре.

### Правила полей

Схема задаёт не только структуру, но и границы: длина заголовка, длина описания,
количество карточек, количество пар в FAQ. Один и тот же документ работает как задание
генератору и как правило проверки на приёмке. Схему следует передать генерирующей стороне
в машинном виде — режим структурированного вывода OpenAI не позволяет модели вернуть
несоответствующую структуру, что убирает основную часть брака на входе.

## 6. Валидация

Проверяется: наличие обязательных полей, соответствие типов, соблюдение границ длины и
количества, доступность каждой ссылки на изображение, корректность домена и локали.

Файл либо принимается целиком, либо отклоняется целиком. Ответ при отказе содержит точный
адрес проблемы (`pages[0].blocks[3].items[2].a: обязательное поле отсутствует`), чтобы
генерирующая сторона могла исправить контент самостоятельно.

## 7. Уникализация

Слоистый конфиг тянет сеть к единообразию, задача сетки — обратная. Разрешение:
**служебные тексты в общем слое хранятся массивом вариантов**, резолвер выбирает вариант
по seed сайта.

```json
"footer.disclaimer": [
  "Материалы носят информационный характер…",
  "Информация предоставлена в ознакомительных целях…",
  "Данный обзор является информационным…"
]
```

Массовая правка остаётся правкой одной строки (меняется список), но идентичного текста
на всех доменах не возникает.

**Оси вариативности,** все производные от `seed = hash(domain)`: палитра, шрифтовая пара,
радиусы и плотность, вариант раскладки каждой секции (hero ×3, cards ×2, columns ×2,
faq ×2), порядок блоков в допустимых пределах, набор необязательных блоков, хеши
CSS-классов, выбор варианта служебного текста.

Первые шесть осей реализуются на этапе 1. Выключение необязательных блоков и выбор
варианта служебного текста зависят от общего слоя, а вариативные хеши CSS-классов — от
постобработки сборки, поэтому все три появляются на этапе 2.

**Детерминированность обязательна:** один seed всегда даёт один результат, поэтому
пересборка не меняет внешний вид уже проиндексированного сайта.

## 8. SEO-артефакты

Генерируются при сборке: `sitemap.xml`, `robots.txt`, canonical, `hreflang` при
мультиязычии, JSON-LD (`FAQPage` для блока вопросов — даёт расширенный сниппет,
`Organization`), страница 404 с `noindex`, корректные `lang`/`dir` и системные шрифтовые
стеки, работающие в любой локали (латиница, арабица, тайское письмо, CJK).

OG-изображение через satori и favicon из лого относятся к этапу 2: оба требуют обработки
изображений, которая появляется вместе с медиа-пайплайном.

## 9. Этапы реализации версии 0

**Этап 1 — Ядро рендера.** Zod-схема блоков, Astro-шаблон с реестром блоков, theme engine.
Ни базы, ни сети: вход — `sites/<domain>.json`, выход — `dist/`.
*Критерий готовности:* десять разных JSON дают десять визуально непохожих рабочих сайтов;
повторный запуск на том же JSON даёт тот же внешний вид (тема и варианты секций не «плывут»).

**Этап 2 — Команда `make-site`.** Валидация, медиа-обработка, резолв двух слоёв, снапшот.
*Критерий:* одна команда превращает файл контента в готовую папку `dist/`, а битый файл
отклоняется с внятной ошибкой.

**Этап 3 — Выкладка.** Cloudflare Pages API, health-check, запись результата.
*Критерий:* **одна команда — и сайт открывается в интернете.** Это законченная версия 0.

**Этап 4 (опционально, +полдня) — Приём по вебхуку.** Маленький обработчик входящих
запросов, вызывающий ту же команду. Нужен, только если генерирующая сторона должна
отправлять контент сама, без ручного запуска. Очередь и Redis для этого не требуются.

## 10. Путь роста

Полная архитектура на случай, когда версия 0 упрётся в масштаб. Каждый пункт добавляется
независимо от остальных и не требует переделки модели данных.

| Компонент | Что даёт | Триггер для добавления |
|---|---|---|
| Очередь (BullMQ + Redis) и параллельные воркеры | Пакетная сборка, retry с backoff, ограничение нагрузки | Больше 5–10 сборок за раз |
| PostgreSQL вместо файлов | Статусы, поиск, одновременная работа нескольких людей | Ручной обход файлов перестаёт быть удобным |
| Directus поверх базы | Админка, роли, история версий, медиа-библиотека для не-разработчика | Правками начинает заниматься не разработчик |
| Ingest API (`POST /sites`) | Приём контента извне с валидацией и идемпотентностью по `external_id` | Генерирующая сторона отправляет контент потоком |
| Cloudflare R2 для медиа | Общий склад картинок, переиспользование между сайтами, независимость от чужих ссылок | Картинки начинают повторяться между сайтами |
| Третий слой конфига (пресеты) | Настройки под нишу и язык между общим и личным слоем | Появляются заметно разные ниши или языки |
| Несколько deploy-адаптеров (Netlify, S3+CDN, VPS) | Разнос сети по провайдерам | Сеть перестаёт помещаться к одному провайдеру |
| DNS-адаптер (Cloudflare API) | Автоматическая привязка домена, SSL, статусы | Ручные привязки начинают отнимать время |
| Dry run + канареечная раскатка | Показ diff и числа затронутых сайтов; сначала 5 сайтов, потом остальные | Массовые правки затрагивают десятки живых сайтов |
| Мониторинг и алерты | Список упавших сборок и недоступных сайтов | Сайтов больше, чем можно проверить глазами |

### Целевая архитектура после полного роста

```
① Ingest API       POST /sites — валидация, идемпотентность по external_id
② Media pipeline   скачивание → sharp → R2 → URL в конфиг
③ PostgreSQL       sites | global_config | presets | builds | domains | media
④ Config resolver  global → preset → site (deep merge)
⑤ Theme engine     seed → тема и варианты секций
⑥ Renderer         Astro: JSON → dist/            (не меняется при росте)
⑦ Build runner     очередь, воркеры, retry
⑧ Deploy adapter   Cloudflare Pages | Netlify | S3+CDN | VPS+rsync
⑨ DNS adapter      Cloudflare API
⑩ Orchestrator     вебхуки Directus → расчёт затронутых сайтов → постановка задач
```

Компоненты ④, ⑤, ⑥ и модель данных переходят из версии 0 без изменений — именно поэтому
их нельзя упрощать на старте.

### DNS при росте

Домены заводятся на Cloudflare как DNS-слой, независимо от регистратора: человек один раз
меняет NS-записи, дальше вся привязка идёт через Cloudflare API. Это снимает зависимость
от API конкретного регистратора и не требует переделки, когда часть доменов окажется
куплена в другом месте.

## 11. Эксплуатация версии 0

- **Идемпотентность:** повторный запуск на том же файле перезаписывает сайт, а не создаёт второй.
- **Ошибки:** упавшая сборка выводит причину и не трогает уже выложенную версию сайта.
- **Health-check:** после выкладки выполняется запрос к адресу сайта; успехом считается
  код 200 и наличие ожидаемой строки в HTML.
- **Откат:** пересборка из снапшота в `.builds/<domain>/`.
- **История:** git-история `global.json` и `sites/` показывает, кто и что менял.

## 12. Открытые вопросы

Уточняются у заказчика, влияют на объём и на момент перехода к росту, но не на архитектуру:

- Количество сайтов и темп появления новых.
- Языки и гео (определяет объём работы по шрифтам и типографике).
- Кто владеет доменами, у какого регистратора.
- Есть ли выделенный человек на контент-правки.
- Бюджет на хостинг и допустимое число провайдеров.

## 13. Рассмотренные и отклонённые альтернативы

- **Nuxt вместо Astro.** Отклонён: 20–40 с на сборку против 2–5 с, лишний JS на страницах
  без интерактива. Vue сохранён на уровне компонентов.
- **Один рантайм-сервер на все домены** (`Host` → конфиг из базы). Отклонён: вся сеть на
  одном IP, один отказ роняет всё. Мгновенность правок не перевешивает.
- **Гибрид (статика + подтягивание правок рантаймом).** Отклонён как основной режим,
  оставлен как возможная опция на уровне отдельного сайта.
- **Несколько независимых шаблонов.** Отклонён на старте: генерируемая тема и варианты
  секций дают сопоставимое разнообразие при кратно меньшей поддержке.
- **Формат контента диктует генератор.** Отклонён: слой-маппер произвольных данных
  становится постоянным источником ошибок и ручных разборов.
- **Git + PR как интерфейс правок для не-разработчика.** Отклонён для полной версии
  (нужна админка), но в версии 0 правки делает разработчик, поэтому git достаточен.
- **Полная архитектура сразу.** Отклонена: девять из десяти компонентов обслуживают масштаб,
  которого пока нет, и добавляются позже без переделки. Вынесена в раздел 10 как путь роста.
