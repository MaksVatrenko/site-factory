# Формат контента v2 — одинаковые блоки, адрес из имени файла, картинки

**Дата:** 2026-09-14
**Статус:** согласован в диалоге, ждёт прочтения
**Заменяет:** формат файла страницы из `docs/content-format.md` — поле `slug`, собственные
поля блоков (`heading`, `paragraphs`, `items`), заголовок вида `{ "tag": "h2", "text": … }`.
Устройство фабрики, шаблонов и схем из `2026-09-07-factory-v1-design.md` не меняется.

## 1. Что и зачем

Сейчас у каждого блока свой набор полей: `hero` — `heading` и `paragraphs`, `toc` — `heading`
и `items`, `faq` — `heading` и `items` из пар `q`/`a`. Только `section` устроен через список
`content`, в котором контент собирается по кусочку. Чтобы поменять местами абзац и заголовок
в `hero` или добавить список в `faq`, нужно помнить устройство каждого блока в отдельности.

Три изменения:

1. **Все блоки устроены одинаково:** `type` плюс `content`. Тип отвечает только за
   оформление секции, состав определяет `content`.
2. **Адрес страницы — это имя файла.** Поле `slug` уходит: `casino.json` — это `/casino`.
3. **Картинки в любом месте:** `{ "image": "main" }`, данные картинки — в `images.json`.

Таблица заказчика (`docs/spreadsheet-format.md`) **не меняется**. Меняется только JSON,
который из неё получается, и то, что пишется руками.

Старый формат уходит целиком, без поддержки рядом с новым — как и при переходе на `SITE_DIR`.

## 2. Файл страницы

```jsonc
// data/sites/899ok/home.json  →  адрес /
{
  "title": "899OK | Bangladesh Casino & Cricket Betting Site",
  "description": "899OK is the Bangladesh casino I actually play on…",
  "blocks": [
    { "type": "hero", "content": [
      { "type": "title", "h1": "899OK — Bangladesh's Everyday Casino & Cricket Book" },
      { "type": "text", "text": "It was a Friday night in Mirpur…" },
      { "image": "main" }
    ]},
    { "type": "toc", "content": [
      { "type": "title", "h2": "What's on This Page" },
      { "type": "list", "items": ["Why 899OK Actually Works for Me", "Cricket Betting"] }
    ]},
    { "type": "section", "content": [
      { "type": "title", "h2": "Why 899OK Actually Works for Me" },
      { "type": "text", "text": "There are maybe two dozen casino sites…" },
      { "image": "casino-lobby" },
      { "type": "list", "items": ["Live dealer tables stay busy…"] },
      { "type": "cards", "items": [
        { "title": "BPL Markets", "text": "Expect 35–50 markets…", "image": "bpl" }
      ]}
    ]},
    { "type": "links", "content": [
      { "type": "title", "h2": "899OK — More Pages" }
    ]},
    { "type": "faq", "content": [
      { "type": "title", "h2": "899OK FAQ — Payments, Safety, Signup" },
      { "type": "toggle", "title": "Is 899OK legit in Bangladesh?", "text": "Yes, in practice…" }
    ]}
  ]
}
```

Поля страницы: `title` и `description` для поисковика, `blocks` — секции по порядку.

### 2.1. Адрес — из имени файла

- `casino.json` → `/casino`. Имя берётся без `.json` и без переделок — регистр, пробелы и
  буквы не меняются, так что что видно в папке, то и будет в адресе. Проходит только ту же
  защитную чистку, что сейчас проходит `slug`: убираются управляющие символы, раскрываются
  `%`-последовательности, режется длина. Рекомендуется латиница в нижнем регистре через
  дефис; импорт из таблицы так и называет файлы.
- **Главная — `home.json`** → `/`. Сравнение без учёта регистра: `Home.json` — тоже главная.
- `site.json` и `images.json` — служебные, страницами не считаются. Их список живёт в одном
  месте (`src/lib/site-dir.mjs`), и сервер фабрики берёт его оттуда же — сейчас у сервера своя
  копия правила «что считать страницей».
- Поле `slug` в файле страницы игнорируется с предупреждением. Без предупреждения забытый
  `"slug": "/promo"` в `bonus.json` молча дал бы `/bonus`.
- Нет `home.json` — предупреждение: у сайта не будет главной. Сборка при этом идёт, как идёт
  сейчас сайт `broken`, у которого нет страницы на `/`.
- Страницы читаются только из корня папки сайта. Подпапки — в том числе `public/` —
  страницами не считаются. Когда появятся языки, то же правило продолжится на подпапки
  (`bn/casino.json` → `/bn/casino`), но в этот объём это не входит.
- Имя файла проходит ту же проверку через файловую систему (`slug-prober.mjs`), что и нынешний
  `slug`: файл `sitemap.xml.json` иначе перезаписал бы карту сайта.
- Порядок страниц не меняется: главная первой, остальные по имени файла.

### 2.2. Блоки

Любой блок — `{ "type": "…", "content": [ … ] }`. Тип выбирает оболочку секции:

| Тип | Оболочка |
|---|---|
| `hero` | Первый экран: плашка с названием бренда, крупный `h1` с градиентом, картинки грузятся сразу |
| `section` | Обычная секция |
| `toc` | Первый `list` в `content` — это оглавление: пункты становятся сеткой ссылок на разделы, сопоставленных по позиции, как сейчас |
| `links` | После `content` выводится сетка ссылок на страницы из `nav` в `site.json` |
| `faq` | Обычная секция; тип сохранён, чтобы позже добавить разметку FAQ для поисковиков |

- **Неизвестный тип** (`"type": "promo"`) выводится как `section` с предупреждением, а не
  выкидывается: раз у всех блоков одинаковое устройство, контент при этом не теряется. Если
  шаблон не объявляет и `section`, блок выкидывается, как сейчас.
- Нет `content` — блок пустой. `links` при этом всё равно выводит сетку страниц, остальные
  не выводят ничего. `content` не список — предупреждение, блок пустой.
- **Остатки старого формата.** У блока есть поля кроме `type` и `content` — предупреждение
  с их именами («поля heading, paragraphs не используются»). Без этого блок, написанный
  по-старому, молча исчез бы со страницы.

### 2.3. Элементы `content`

| Элемент | Вид | Что это |
|---|---|---|
| Заголовок | `{ "type": "title", "h2": "текст" }` | Ключ — это тег, от `h1` до `h6` |
| Абзац | `{ "type": "text", "text": "…" }` | Без изменений |
| Список | `{ "type": "list", "items": ["…"] }` | Без изменений |
| Таблица | `{ "type": "table", "columns": […], "rows": [[…]] }` | Без изменений |
| Карточки | `{ "type": "cards", "items": [{ "title", "text", "image" }] }` | Появилось необязательное `image` |
| Раскрывашка | `{ "type": "toggle", "title": "…", "text": "…" }` | **Новый.** Работает в любой секции, не только в `faq`. Та же плавная анимация, что сейчас у FAQ |
| Картинка | `{ "image": "main" }` | **Новый.** Имя из `images.json`, см. раздел 3 |

Ссылки `[текст](/адрес)` работают, как и сейчас, в любом тексте — теперь и в `toggle`.

**Заголовок.** Берётся первый ключ из `h1`–`h6` в том порядке, в каком он записан в объекте.
Если таких ключей несколько — используется первый, остальные игнорируются с предупреждением.
Нет ни одного, или значение не непустая строка — заголовок выкидывается с предупреждением.

**Картинка** пишется и как `{ "type": "image", "image": "main" }` — это то же самое, без
предупреждения: так её напишут по аналогии со всеми остальными элементами.

### 2.4. Один `h1` на страницу

Проверяется по всей странице, в порядке блоков и элементов. Первый `h1` остаётся, каждый следующий
становится `h2` с предупреждением. Если на странице есть содержимое, но нет ни одного `h1` —
предупреждение: для SEO это потеря, но сборка идёт. Страница, на которой нет вообще ничего, об `h1`
не предупреждает — ей нечего озаглавливать.

## 3. Картинки: `images.json`

### 3.1. Формат

Лежит рядом с `site.json`, необязателен:

```json
{
  "main": { "src": "/images/main.webp", "alt": "Логотип 899OK на тёмном фоне" },
  "bpl":  { "src": "/images/bpl.webp", "alt": "Табло матча BPL", "width": 800, "height": 450 }
}
```

| Поле | Что это |
|---|---|
| ключ | Имя, по которому картинку вызывают из контента. Точное совпадение, с учётом регистра |
| `src` | Путь от корня сайта (`/images/main.webp`) или адрес `https://…` |
| `alt` | Описание картинки для поисковика и экранного диктора |
| `width`, `height` | Необязательно. Если указаны, страница не прыгает, пока картинка грузится |

**Любые другие поля игнорируются.** Когда картинки начнут генерироваться через runware.ai,
генератор сможет хранить рядом свой `prompt` или id — сборке это не помешает.

**Файлы** лежат в `data/sites/<сайт>/public/images/`. В сборку они попадают существующим
механизмом копирования `public/`; ссылки на них в превью уже переписываются сервером.

### 3.2. Где работает `image`

Элемент `content`, у которого нет `type` (или `type` равен `image`) и есть ключ `image`, — это
картинка. У элемента с любым другим `type` ключ `image` — это его поле, как у карточки.

- Отдельным элементом в `content` любого блока.
- Полем `image` у любого объекта внутри `content` — сейчас это карточка. Движок ищет ключ
  `image` на любой глубине, не разбираясь, что за элемент перед ним, поэтому новому элементу
  с картинкой ничего дописывать в движок не придётся.
- `brand.logo` в `site.json` — теперь тоже имя из `images.json`, а не путь. Сейчас логотип
  не указан ни у одного сайта, так что переводить нечего.

### 3.3. Как имя становится картинкой

Для каждого имени движок отвечает: вот `{ src, alt, width, height }` — или почему нельзя.
Всё, что не сложилось, не роняет сборку: картинка не выводится, в лог уходит предупреждение.

| Случай | Что происходит |
|---|---|
| Имени нет в `images.json` (или файла `images.json` нет) | Не выводится, предупреждение |
| У записи нет `src` или он не строка | Не выводится, предупреждение |
| `src` — путь, а файла в `public/` нет | Не выводится, предупреждение (как сейчас с логотипом) |
| `src` с другой схемой (`data:`, `javascript:`, …) или с `..` в пути | Не выводится, предупреждение |
| `src` — `https://…` | Используется как есть, на диске не проверяется |
| `src` без ведущего `/` (`images/x.webp`) | Дополняется до `/images/x.webp` |
| Нет `alt` | **Выводится** с пустым `alt`, предупреждение |
| `width`/`height` не положительные целые (строка `"800"` принимается) | Игнорируются |
| `images.json` — не объект, или запись в нём — не объект | Игнорируется, предупреждение |
| `images.json` — не JSON | Сборка падает, как с любым нечитаемым файлом контента |

У элемента-картинки, который не сложился, выкидывается весь элемент; у карточки — только её
поле `image`, сама карточка остаётся.

### 3.4. Вывод

Обычный `<img>` по ширине контейнера, со скруглением по стилю шаблона. `loading="lazy"`
везде, кроме блока `hero`: там `loading="eager"` и `fetchpriority="high"` — картинка первого
экрана, отложенная до прокрутки, проседает в метрике скорости загрузки (LCP), которую считает
поисковик. `width`/`height` выводятся, если указаны.

## 4. Архитектура

Подход: **движок приводит контент к одному виду, шаблон только рисует.** Два правила этого
формата нельзя выполнить внутри компонента шаблона: «один `h1` на страницу» требует видеть
всю страницу, а проверка файла картинки требует диска. Поэтому разбор заголовков и картинок —
в движке, шаблон получает готовые данные.

### 4.1. Кто за что отвечает

| Файл | Что делает |
|---|---|
| `src/lib/site-dir.mjs` | Адрес из имени файла, `home.json` → `/`. Читает `images.json`. Держит список служебных имён. Предупреждает об оставшемся `slug` и об отсутствии `home.json` |
| `src/lib/images.mjs` *(новый)* | Разбирает `images.json` в реестр; по имени отдаёт картинку или причину отказа (раздел 3.3). О диске знает только через переданную ему функцию «есть ли файл» |
| `src/lib/content.mjs` *(новый)* | Приводит `content` одной страницы: заголовки, картинки на любой глубине, правило одного `h1`, остатки старых полей |
| `src/lib/normalize.mjs` | Вызывает `content.mjs` для каждой страницы. Неизвестный тип блока → `section` |
| `src/lib/site-context.mjs` | Передаёт в нормализатор функцию проверки файла в `publicDir`. Прежняя отдельная проверка логотипа уходит — логотип теперь картинка из реестра |
| `src/lib/anchors.mjs` | Заголовок любого блока — первый `title` в `content`. В `toc` оглавлением считается первый `list` |
| `factory/server.mjs` | Счётчик страниц в выпадашке берёт список служебных имён из `site-dir.mjs` |
| `templates/review/blocks/*` | Все пять блоков рисуют `content` через `ElementRenderer`, каждый в своей оболочке. `hero` передаёт своим картинкам, что их нужно грузить сразу, — это решение вёрстки, движок про загрузку не знает |
| `templates/review/elements/image.astro`, `toggle.astro` *(новые)* | Картинка и раскрывашка |
| `templates/review/elements/cards.astro` | Картинка у карточки |
| `templates/review/Heading.astro` | Принимает `h1`: у него градиент и нет полосы, у `h2`–`h6` — полоса, как сейчас |
| `templates/review/manifest.json` | `elements` дополняется `image` и `toggle` |
| `scripts/sheet-to-json.mjs`, `scripts/import-sheet.mjs` | Новый формат, без `slug`, главная всегда `home.json` (раздел 6) |

Проверка файла подключается к `normalizeSite` снаружи — так же, как сейчас подключается
проверка слагов. Ядро остаётся чистой функцией, и модульным тестам не нужен настоящий диск.

### 4.2. Что приходит в шаблон

Внутренний вид, который получают компоненты шаблона, отличается от того, что пишется в файле:

- заголовок — `{ type: "title", tag: "h2", text: "…" }`: те же поля, что у нынешнего
  элемента, поэтому `title.astro` почти не меняется;
- картинка — `{ type: "image", image: { src, alt, width?, height? } }`;
- у карточки поле `image` — такой же объект `{ src, alt, … }` или отсутствует;
- у первого `list` в `toc` — пункты уже сопоставлены с якорями разделов.

### 4.3. Граница движка

Движок узнаёт по имени ровно два элемента: `title` (из-за правила одного `h1` и якорей) и
`image` (из-за реестра и диска). Плюс, как и сейчас, `anchors.mjs` знает про `toc` — и теперь
про первый `list` внутри него, потому что оглавление живёт там. Про
`text`, `list`, `table`, `cards`, `toggle` и любой будущий элемент движок не знает ничего — они
проходят к шаблону как есть. Ключ `image` внутри любого из них движок подставляет, не зная,
чей это ключ.

### 4.4. Путь данных

```
data/sites/<сайт>/
  home.json, casino.json …  ──┐
  site.json                   ├─ site-dir.mjs ─ адрес из имени, реестр картинок
  images.json               ──┘        │
                                       ▼
                             normalize.mjs ─ настройки, слаги (через пробер),
                                       │     блоки, неизвестный тип → section
                                       ▼
                             content.mjs ─ title h2:"…" → {tag, text}
                                       │   image → images.mjs → {src, alt}
                                       │   один h1 на страницу
                                       ▼
                             anchors.mjs ─ якоря, оглавление по позиции
                                       ▼
                             шаблон ─ блок → ElementRenderer → элемент
```

## 5. Кривой контент

**Предупреждения, сборка идёт:** остался `slug` в файле; нет `home.json`; у блока поля кроме
`type` и `content`; `content` не список; неизвестный тип блока; у заголовка нет ключа
`h1`–`h6`, или их несколько, или пустое значение; второй `h1`; на странице нет `h1`; все случаи
картинок из раздела 3.3.

**Сборка падает — как и сейчас, только в двух случаях:** файл контента не читается или не JSON
(теперь это касается и `images.json`); в папке нет ни одной страницы.

Все предупреждения видны в логе фабрики, как сейчас.

## 6. Конвертер и импорт

- `sheetToPage(csv)` больше не принимает слаг и не пишет его. Возвращает
  `{ title, description, blocks }` в новом формате.
- `hero` собирается так же, как `section`: `title` с `h1`, потом абзацы и списки по порядку.
  Особый путь для `hero` (абзацы отдельно, списки отдельно, порядок между ними теряется)
  исчезает.
- `toc` → `title` + `list`; `faq` → `title` + `toggle` на каждый вопрос; `links` → `title`;
  заголовки — `{ "type": "title", "h2": "…" }`. Правило карточек и правило оглавления не меняются.
- `import:sheet` выбирает только имена файлов: лист главной (`Home`, `Index`, `Main`,
  `Главная`, `Домашняя`) → всегда `home.json`, остальные → имя листа. Совпадение имён двух
  листов по-прежнему разводится суффиксом `-2` с предупреждением. Меню в заготовке `site.json`
  строится из имён файлов.

## 7. Перевод существующих данных

- **`data/sites/899ok/`** переводится разовым скриптом, а не повторным импортом таблицы:
  повторный импорт стёр бы ссылки `[текст](/casino)` и карточки, проставленные после него.
  Файлы уже названы по адресам (`home.json`, `casino.json`, …), так что переименовывать ничего
  не нужно — только убрать `slug` и перестроить блоки. Скрипт в репозиторий не попадает.
- **`data/sites/broken/`** переписывается руками: он должен ломать уже новый формат. Туда
  входят: блок по-старому (`heading`, `items`), заголовок без ключа, два `h1`, картинка с
  неизвестным именем, картинка без `src`, `images.json` с записью-строкой, неизвестный тип блока,
  оставшийся `slug`. Главной у него по-прежнему нет — это покрывает путь сервера для сайта
  без `/`.
- **`docs/content-format.md`** и **`docs/content-template.json`** переписываются под новый
  формат. В `docs/spreadsheet-format.md` добавляется одна строка: лист главной называется `Home`.

## 8. Тесты

**Новые модульные:** `images.mjs` — все строки таблицы из раздела 3.3; `content.mjs` —
заголовки, картинка отдельным элементом и в карточке, оба написания картинки, правило одного
`h1`, предупреждение об отсутствии `h1`, остатки старых полей; `site-dir.mjs` — адрес из имени,
`home.json` в любом регистре, служебные имена, оставшийся `slug`, отсутствие `home.json`;
`normalize.mjs` — неизвестный тип → `section`; `anchors.mjs` — первый `title` у любого блока,
оглавление из первого `list`.

**Новые сквозные:** картинка выводится с `src` и `alt`; `lazy` в секции и `eager` в `hero`;
картинка у карточки; логотип из `images.json`; ненайденная картинка не выводится и видна в логе;
`toggle` выводит раскрывашку; неизвестный тип блока выводится как секция; счётчик страниц на
сервере не считает `images.json`.

**Тесты на опасные слаги.** Сейчас они подсовывают `..`, `/`, 300 символов и одиночные
суррогаты через поле `slug`. Большинство из этого не может быть именем файла, так что сквозными
тестами эти случаи больше не воспроизвести:

- **остаются модульными.** `normalizeSite` по-прежнему принимает сырой слаг — его теперь
  подставляет переходник, а не автор, — так что все проверки `buildSlugCandidate` и пробера
  остаются как есть;
- **сквозные переезжают на опасные имена файлов**, которые реально могут существовать:
  `sitemap.xml.json`, `index.html.json`, `robots.txt.json`, `%41.json`;
- помощник `writeSiteDirFromContent` пишет каждую страницу в файл `<адрес>.json` (`/` →
  `home.json`) и **падает**, если адрес нельзя сделать именем файла. Иначе тест, чей сценарий
  стал невозможен, продолжал бы проходить, проверяя уже не то.

Остальные тесты переводятся на новый формат фикстур без изменения того, что они проверяют.

## 9. Что не входит

- Метка картинки в таблице заказчика — картинки пока вставляются только в JSON.
- Генерация картинок через runware.ai — формат `images.json` к ней готов (раздел 3.1).
- Подпапки и языки (`bn/casino.json`).
- Обработка картинок: пережатие, размеры под экран, конвертация форматов, чтение
  `width`/`height` из самого файла.
- Картинка справа от текста в `hero` и любые другие раскладки — картинка выводится там, где
  стоит в `content`. Раскладку продиктует заказчик.
- Разметка FAQ для поисковиков.
