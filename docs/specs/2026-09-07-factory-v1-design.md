# Фабрика сайтов v1 — вертикальный срез

**Дата:** 2026-09-07
**Статус:** согласован, готов к планированию
**Заменяет:** решения о теме, валидации и способе запуска из `2026-09-01-site-factory-design.md`

## 1. Что это и зачем

Локальный конвейер: запускаешь `npm run dev`, открывается браузер, заполняешь форму,
жмёшь «Сгенерировать» — в `output/<домен>/` появляется готовый статический сайт.

Это **вертикальный срез**: сквозной рабочий путь в минимальном объёме. Внутри сразу три
шаблона и три цветовые схемы, но интерфейс — только то, что нужно для запуска. Три
остальные вкладки существуют как заглушки, чтобы каркас конвейера был виден целиком.

## 2. Чем это отличается от спека 2026-09-01

Три решения предыдущего спека пересмотрены. Остальное (статическая раздача, блочная
модель контента, многостраничная схема, инвариант «рендер ничего не знает о хостингах»)
остаётся в силе.

| Было | Стало | Почему |
|---|---|---|
| Тема генерируется из `seed = hash(domain)` | Три готовых шаблона + три цветовые схемы, выбор явный | Предсказуемый результат: видно заранее, что получится. Seed-тема давала разнообразие ценой контроля |
| Zod-схема и валидация на входе | Нормализатор без схемы, сборка не падает никогда | Валидация отклоняла файл целиком; на этапе отладки конвейера это тормозит больше, чем помогает |
| Запуск командой `make-site file.json` | Веб-интерфейс на `localhost:3002` | Форма с выпадайками вместо редактирования JSON руками |
| «Несколько независимых шаблонов» отклонены (раздел 13) | Шаблоны приняты, но как плагины одного движка | Отклонение касалось *независимых проектов*. Плагины дают разнообразие без дублирования общего кода |

## 3. Архитектура

Три слоя. Каждый понимается и проверяется отдельно.

```
┌─ Фабрика (factory/) ──────────────────────────────────┐
│  Express-сервер + статический UI.                     │
│  Знает про папки и команды. Не знает про вёрстку.     │
└───────────────────┬───────────────────────────────────┘
                    │ запускает дочерним процессом
                    ▼
┌─ Движок (src/) ───────────────────────────────────────┐
│  Astro. Чистая функция:                               │
│  site.json + шаблон + схема → output/<домен>/         │
│  Не знает про UI, сервер, домены, хостинги.           │
└───────────────────┬───────────────────────────────────┘
                    │ подставляет по манифесту
                    ▼
┌─ Шаблоны (templates/tN/) ─────────────────────────────┐
│  manifest.json + Vue-компоненты блоков.               │
│  Не знают друг о друге и о движке.                    │
└───────────────────────────────────────────────────────┘
```

**Ключевая граница:** в коде движка ни разу не упоминается `t1`, `t2` или `t3`. Движок
читает манифест выбранного шаблона и подставляет компоненты по типу блока. Четвёртый
шаблон — это положить папку, ничего не правя.

## 4. Раскладка на диске

```
package.json               один на весь проект
astro.config.mjs           outDir и site читаются из переменных окружения

src/                       движок
  layouts/Base.astro       html/head, meta, инлайн цветовой схемы
  pages/[...slug].astro    getStaticPaths из pages[]
  components/BlockRenderer.astro   выбор компонента по type
  lib/normalize.mjs        нормализация входного JSON
  lib/templates.mjs        чтение манифестов
  lib/schemes.mjs          чтение CSS-схем

templates/t1/manifest.json + blocks/*.vue
templates/t2/…             те же блоки, другая вёрстка
templates/t3/…

styles/base.css            сброс, типографика на переменных
styles/schemes/blue.css    :root { --c-* }
styles/schemes/green.css
styles/schemes/dark.css

data/examples/<папка>/site.json   контент (+ images/ при наличии)
output/<домен>/            результат сборки

factory/server.mjs         Express: API + статика
factory/public/            index.html, app.js, styles.css

tests/                     Vitest
```

## 5. Формат шаблона

`templates/t1/manifest.json`:

```json
{
  "id": "t1",
  "name": "Template 1",
  "description": "Классический: широкий hero, сетка карточек 3×",
  "blocks": ["hero", "richtext", "cards", "columns", "faq", "footer"],
  "defaultScheme": "blue"
}
```

Рядом `blocks/Hero.vue`, `blocks/Cards.vue` и так далее — по одному файлу на тип из
`blocks`. Правило сопоставления: тип блока `richtext` → файл `blocks/RichText.vue`
(PascalCase от типа). Если шаблон не заявляет тип блока, блок пропускается с записью
в лог. Если заявляет, но файла нет — это ошибка шаблона, сборка отказывает: такое
чинится в коде, а не терпится молча.

Все три шаблона поддерживают одинаковый набор из шести блоков — это делает их
**взаимозаменяемыми**: один и тот же контент-JSON собирается любым шаблоном.

## 6. Формат контента

Контент приходит готовым JSON извне. Схемы и валидации нет.

```jsonc
{
  "domain": "example.com",
  "locale": "en-US",
  "brand": { "name": "Example", "logo": "images/logo.png" },
  "pages": [
    {
      "slug": "/",
      "meta": { "title": "…", "description": "…" },
      "blocks": [
        { "type": "hero",     "props": { "title": "…", "subtitle": "…", "cta": "…" } },
        { "type": "richtext", "props": { "heading": "…", "paragraphs": ["…"] } },
        { "type": "cards",    "props": { "items": [{ "title": "…", "text": "…" }] } },
        { "type": "columns",  "props": { "items": [{ "title": "…", "links": ["…"] }] } },
        { "type": "faq",      "props": { "items": [{ "q": "…", "a": "…" }] } }
      ]
    }
  ]
}
```

Футер в контенте не приходит: движок сам дописывает блок `footer` в конец каждой страницы
и берёт его компонент из шаблона, как и любой другой блок. Тексты футера (дисклеймер,
копирайт) на этом этапе живут в компоненте шаблона; вынос в общий слой — следующая итерация.

Картинки из `data/examples/<папка>/images/` копируются в корень собранного сайта, поэтому
относительные пути вида `images/logo.png` в контенте работают без изменений.

### Нормализатор вместо валидатора

`src/lib/normalize.mjs` приводит любой вход к пригодной для рендера форме:

| Ситуация | Поведение |
|---|---|
| Файл не читается или не JSON | Единственный случай отказа: понятная ошибка, сборка не стартует |
| Нет `pages` или массив пуст | Одна пустая страница `/`, предупреждение в лог |
| Нет `meta.title` | Берётся название бренда |
| У блока нет `props` | Пустой объект |
| Тип блока неизвестен шаблону | Блок пропускается, предупреждение в лог |
| Массив ожидался, пришла строка | Оборачивается в массив |
| Лишние поля | Игнорируются молча |

**Сборка не падает никогда.** Кривой блок означает сайт без этого блока, а не красную
ошибку. Что пропущено — видно в логе.

## 7. Цветовые схемы

`styles/schemes/blue.css` — только переменные:

```css
:root {
  --c-bg: #ffffff;
  --c-fg: #1a1f2e;
  --c-primary: #2563eb;
  --c-primary-fg: #ffffff;
  --c-muted: #64748b;
  --c-surface: #f1f5f9;
  --c-border: #e2e8f0;
}
```

Движок читает выбранный файл при сборке и инлайнит в `<head>` через `set:html` — ноль
внешних запросов, ноль дополнительных файлов.

**Приоритет:** значение из UI → поле `style` в JSON → `defaultScheme` шаблона.

Новая схема = положить `.css` в папку. UI подхватит сам: список схем строится сканированием
директории, нигде не захардкожен.

## 8. Интерфейс

`npm run dev` поднимает сервер на `localhost:3002` и открывает браузер.

Четыре вкладки: **Генерация** (работает), **Массовая генерация**, **Скачать с сервера**,
**Проекты** (заглушки с надписью «в разработке»).

### Вкладка «Генерация»

Четыре карточки, как на референсе:

| Карточка | Поля |
|---|---|
| Основное | Бренд, Гео, Язык |
| Шаблон и контент | Шаблон, Цветовая схема, Папка с примерами |
| Сайт и партнёрка | Адрес сайта, Ссылка партнёрки |
| Результат | лог сборки, ссылка «Открыть», кнопка «Скачать zip» |

Выпадайки «Шаблон», «Цветовая схема» и «Папка с примерами» заполняются с сервера
сканированием соответствующих директорий.

Ниже — кнопка «Сгенерировать» и строка статуса.

### Как поля попадают в сайт

| Поле | Куда идёт |
|---|---|
| Бренд | Название в шапке, футере, `<title>` при отсутствии meta |
| Гео | `meta[name=geo.region]`, метаданные проекта |
| Язык | `<html lang>`, `hreflang`, направление письма |
| Шаблон | Выбор папки `templates/tN/` |
| Цветовая схема | Инлайн CSS-переменных |
| Папка с примерами | Источник `site.json` и картинок |
| Адрес сайта | `canonical`, `sitemap.xml`, имя папки в `output/` (при пустом поле — имя папки с примерами) |
| Ссылка партнёрки | Все CTA-кнопки шаблона (hero, карточки, футер) |

Значения из формы перекрывают одноимённые поля JSON.

### API

| Метод | Назначение |
|---|---|
| `GET /api/templates` | Список шаблонов из манифестов |
| `GET /api/schemes` | Список схем из `styles/schemes/` |
| `GET /api/examples` | Список папок из `data/examples/` |
| `POST /api/generate` | Запуск сборки, возвращает `buildId` |
| `GET /api/build/:id/log` | Поток лога (SSE) |
| `GET /api/output/:domain/zip` | Архив собранного сайта |
| `GET /preview/:domain/*` | Отдача собранного сайта для просмотра |

Сборка запускается дочерним процессом с переменными окружения:

```
TEMPLATE=t2 SCHEME=blue SITE_JSON=data/examples/foo/site.json \
OUT_DIR=output/example.com SITE_URL=https://example.com \
BRAND=… GEO=… LOCALE=… PARTNER_URL=… npx astro build
```

## 9. Технические решения

**Стек:** Astro 7.3, Vue 3.5 (только как язык описания компонентов, ноль клиентского JS),
Express 5.2, Vitest 5. Node ≥ 22.12.0 (требование Astro 7; нечётные версии не поддерживаются).

**JavaScript, не TypeScript.** Первый срез пишется на чистом ESM. Причина: строгую
типизацию мы и так сняли вместе с Zod-валидацией, а TypeScript 7 — свежий мажор, чей
риск на старте не окупается. Типы вернутся, когда формат данных устоится; JSDoc там,
где сигнатура неочевидна.

**UI без фреймворка.** Форма из восьми полей и лог сборки не требуют React. Нулевая
сборка UI означает мгновенный старт `npm run dev`. API останется прежним, если интерфейс
позже переедет на Vite.

**Ноль клиентского JS в сайтах.** Ни один компонент не получает директиву `client:*`.

**Шрифты системные.** Внешние шрифтовые сервисы не подключаются: лишний запрос и риск
для нелатинских локалей.

## 10. Что не входит

Со скриншота-референса намеренно отложено:

- **Режим генерации контента** («С поиском и SEO» / «Обычная») — контент приходит готовым, генерировать нечего.
- **Язык по умолчанию (.htaccess)** — относится к настройке хостинга.
- **Google-аккаунт (верификация)** — отдельная фича с хранением аккаунтов.
- **Приложение / установка PWA** — manifest, service worker, иконки из логотипа.
- **Заливка на сервер** — кнопка пока только собирает и отдаёт zip.
- Массовая генерация, список проектов, скачивание с сервера — заглушки.

Показывать нерабочие поля в форме хуже, чем не показывать: они создают ложное
представление о готовности.

## 11. Проверка

| Что проверяется | Как |
|---|---|
| Нормализатор | Юнит-тесты: пустой файл, нет `pages`, блок без `props`, мусорный тип, строка вместо массива |
| Чтение манифестов и схем | Юнит-тесты на сканирование директорий |
| Сборка | Автотест: три шаблона на одном контенте (по одной сборке на шаблон) |
| Полная матрица 3×3 | Отдельный скрипт `npm run check:matrix`, запускается руками — девять сборок Astro слишком долги для обычного прогона тестов |
| Взаимозаменяемость | Один контент-JSON проходит через все три шаблона |
| Схемы применились | В выходном HTML присутствуют переменные выбранной схемы |
| Ноль JS | В выходном HTML нет подключённых скриптов |
| API фабрики | Тесты эндпоинтов: списки не пусты, генерация отдаёт `buildId` |

## 12. Критерии готовности

- `npm run dev` поднимает интерфейс и открывает браузер.
- Форма заполняется списками, прочитанными с диска, а не захардкоженными.
- «Сгенерировать» собирает сайт в `output/<домен>/`, лог виден в браузере живьём.
- Готовый сайт открывается по ссылке и скачивается архивом.
- Три шаблона визуально различимы на одном и том же контенте.
- Три цветовые схемы работают на каждом шаблоне.
- Битый JSON даёт сайт с пропущенными блоками и предупреждениями в логе, а не отказ.
- `npm test` проходит целиком.

## 13. Путь дальше

Порядок не зафиксирован, каждый пункт независим:

1. Заливка на сервер по кнопке (FTP/SSH/Cloudflare) — прямое продолжение zip.
2. Вкладка «Проекты»: список собранного с датами и пересборкой.
3. Массовая генерация: список доменов → очередь сборок.
4. PWA: manifest, service worker, иконки из логотипа.
5. Верификация Google, `.htaccess`, редиректы.
6. Список гео с преднастроенными локалями и валютами.
7. Медиа-пайплайн: сжатие картинок, webp/avif.
