# Фабрика сайтов

Локальный конвейер: форма в браузере → готовый статический сайт в `output/<домен>/`.

## Требования

Node.js ≥ 22.12.0 (чётные версии; v23 не поддерживается).

## Запуск

```bash
npm install
npm run dev
```

Открывается `http://localhost:3002`. На вкладке «Генерация» выбираются шаблон, цветовая схема и
папка; кнопка «Сгенерировать» пишет тексты, рисует логотип и картинки, собирает сайт и показывает
лог живьём. Готовое открывается по ссылке или скачивается архивом.

## Сборка без интерфейса

```bash
SITE_DIR=data/sites/899ok \
TEMPLATE=template1 SCHEME=dark OUT_DIR=output/899ok-bd.net \
SITE_URL=https://899ok-bd.net \
npm run build:site
```

Переменные: `SITE_DIR` (папка с сайтом), `PUBLIC_DIR` (картинки), `TEMPLATE`, `SCHEME`,
`OUT_DIR`, `SITE_URL`, а также необязательные `BRAND`, `GEO`, `LOCALE`, `DOMAIN`,
`PARTNER_URL` — они перекрывают одноимённые поля контента. `SITE_DIR` обязателен:
без него сборка падает с понятной ошибкой.

## Новый сайт из таблицы

Заказчик присылает таблицу, где один лист — одна страница. Вся папка сайта
собирается из неё одной командой:

```bash
npm run import:sheet -- 19euPydRRVrAQR_0PMh_j21HF9KaeKC4-mp5bWJmdoWE 520bdapp
```

Первый аргумент — таблица, второй — имя папки сайта. Вместо id можно передать и
целую ссылку, но тогда её нужно взять в кавычки: `?` в адресе zsh принимает за
шаблон имени файла и обрывает команду с `no matches found` ещё до запуска
скрипта.

```bash
npm run import:sheet -- 'https://docs.google.com/spreadsheets/d/19euPy…/edit?gid=1469241983' 520bdapp
```

Скрипт сам находит листы, скачивает каждый, превращает в страницу и раскладывает
в `data/sites/<имя сайта>/`: лист `Home` становится главной, остальные получают
адрес по своему названию. Рядом создаётся заготовка `site.json` с уже собранным
меню. Существующий `site.json` не перезаписывается.

Дописать в нём нужно только то, чего не знает форма: футер, а при желании слоган
и логотип. Бренд, домен, язык, гео и партнёрскую ссылку форма перекрывает при
сборке — в файле они лежат как значения по умолчанию для сборки из командной
строки.

Таблица должна быть доступна по ссылке. Что в ней писать — `docs/spreadsheet-format.md`,
этот документ и передаётся заказчику.

## Картинки и логотип

Картинку на страницу ставит метка `{ "image": "имя" }`. Если такого имени ещё нет в
`images.json` сайта, фабрика перед сборкой сама генерирует картинку через Runware:

- берёт случайный промпт из `factory/prompts/images.json`;
- кладёт файл в `data/sites/<сайт>/public/images/`;
- дописывает `images.json`.

Готовые картинки повторно не генерируются. Галочка «Без генерации картинок и логотипа» в
форме пропускает оба шага. Чтобы перегенерировать картинку, удалите её запись из `images.json`;
у логотипа для этого есть отдельная галочка — см. ниже.

Ключ Runware хранится в файле `.env` в корне проекта. Этот файл не попадает ни в git, ни в
собранный сайт.

```bash
cp .env.example .env                 # затем вписать RUNWARE_API_KEY
npm run generate:images -- 899ok     # логотип и картинки, без сборки
```

Логотип фабрика делает сама, если в `site.json` нет своего `brand.logo`. Ideogram 4.0 рисует
название бренда в случайном стиле из `factory/prompts/logo.json`, модель удаления фона от
Ideogram вырезает её из фона. Получаются
две картинки в `images.json`: `logo` для шапки и `logo-square` — квадрат 512×512 на градиенте.
Квадрат идёт в превью ссылки, в иконку сайта и в разметку schema.org. Чтобы получить другой
вариант, поставьте галочку «Перегенерировать логотип заново»: фабрика нарисует новый стиль и
переключит на него `images.json` (примерно $0.07 за сборку). Старые файлы она не перезаписывает и
не удаляет — они остаются в `public/images/` и попадают в собранный сайт, так что лишние стоит
убрать руками. Свой `brand.logo` из `site.json` галочка не трогает. Модели задаются в `.env`:
`RUNWARE_LOGO_MODEL` и `RUNWARE_BG_MODEL`.

Подробности — в `docs/specs/2026-09-15-image-generation-design.md` и
`docs/specs/2026-09-15-logo-generation-design.md`.

## Как пишутся тексты

Одна кнопка делает сайт целиком: тексты, картинки, логотип, сборка. На входе шаблон, имя папки,
бренд, гео и язык. Страницы не выбираются: сайт — это ровно те страницы, для которых у шаблона есть
примеры, все до одной. Прислали примеры на восемь страниц — будет восемь; на десять — будет десять.
Форма показывает список, чтобы было видно, что получится. Имя папки примера становится адресом
страницы: `bonus/` → `/bonus`.

Поля «Гео» и «Язык» — выпадающие списки: их наполняет таблица страна → язык из
`factory/geos.json`. Выбор гео сразу подставляет её язык в поле рядом (менять дальше можно
свободно), а пустое поле языка означает «взять по гео». Чтобы добавить страну, допишите строку в
`factory/geos.json` — код трогать не нужно, порядок строк в файле — это и есть порядок в
выпадающем списке.

Страницу описывают две разные вещи, и различать их стоит с самого начала. Тема — это то, что в
форме называется «Шаблон», а в командах `--template`: папка `templates/<id>/`. Она отвечает за то, как
блоки выглядят, и ещё за две вещи, которых пример сказать не может: в каком блоке стоит картинка и
сколько ссылок разрешено блоку и странице. Это `templates/<id>/pictures.json`, и больше тема о
странице ничего не решает.

Всё остальное — какие блоки, в каком порядке, что стоит внутри каждого, сколько там пунктов и какой
длины текст — читается из **примера**: готовой страницы, которую прислал SEO. Примеры лежат в
`templates/<id>/examples/<адрес>/<источник>.json` — папка на страницу сайта, файл на сайт-источник.
Фабрика снимает с примера состав и повторяет его: те же блоки в том же порядке, те же элементы в том
же порядке внутри блока, столько же пунктов в списке и примерно такой же длины абзацы — причём
длина берётся из того самого места, где абзац стоит. Если в примере первый экран написан на 375
знаков, а подводка раздела на 51, так и выйдет. Тексты при этом пишутся заново, под свой бренд.

Модель не спрашивают, что положить в блок. Это знает пример, поэтому вопроса нет ни в схеме запроса,
ни в брифе: ответ, который никто не читает, — это оплаченный вывод, а ответ, разошедшийся с
собираемой страницей, был бы хуже бесполезного. У модели остаётся то, что и должно быть её: о чём
раздел, какими словами, на какие страницы сослаться.

Оглавление и «Другие страницы» фабрика заполняет сама, и что бы ни стояло в примере на их месте,
оттуда не читается. Оглавление собирается по блокам с собственным заголовком — поэтому в нём есть и
«Частые вопросы».

Картинка стоит там, где её ставит `pictures.json`, и больше нигде. В присланных примерах картинок
нет ни на одной из 32 страниц, так что взяться им, кроме как от темы, неоткуда. В теме «Шаблон 1»
такой блок один — первый экран, — поэтому картинка на странице одна и она наверху. Имя ей
по-прежнему придумывает модель, место — нет. Если имя вернулось негодным — пустым после очистки,
повторяющим соседнее или занятым логотипом, — блок останется без картинки, а в логе будет строка об
этом: придумать имя за модель нельзя, придуманное дойдёт до `images.json` и будет нарисовано.

Пример выбирает фабрика: каждой странице свой, по зерну от имени папки. Поэтому сайты сети
отличаются друг от друга составом. Повторный запуск той же папки даёт те же примеры и пропускает уже
написанные страницы. Либо пример выбирает владелец — выпадающим списком «Пример» рядом с шаблоном
или флагом `--example`; тогда весь сайт собирается по одному источнику. Выбранный пример записан в
файле страницы полем `example`: движок его не читает и на готовый сайт не выводит, оно говорит
только, с чего страница списана.

Чтобы добавить пример, его импортируют из таблицы:

```bash
npm run import:sheet -- "data/examples-new/книга.xlsx" --example template1/899ok
```

Книга раскладывается по папкам страниц, по файлу `899ok.json` в каждой. Имя одно на все страницы —
по нему один источник можно попросить сразу на весь сайт. Страница, у которой такого примера нет,
назовётся в отказе до первого платного запроса.

Всё делается одним запросом: сначала тексты, потом логотип и картинки, потом сборка. Каждый этап
пропускает сделанное — написанная страница не переписывается, существующий логотип не
перерисовывается, — так что остановившийся прогон доводится повторным нажатием той же кнопки.
Галочка «Только пересобрать, тексты не писать» — это прежняя «Генерация»: папка должна уже быть.

Из командной строки тексты пишутся отдельно:

```bash
npm run generate:texts -- --template template1 --out 520bdapp \
  --brand "520BD" --geo Bangladesh --example 899ok
```

`--example` необязателен: без него каждая страница получает свой пример, как и при пустом поле в
форме. Есть ещё `--pages home` — он сужает прогон до перечисленных страниц, и нужен ровно для
одного: платной пробы. Прогон одной страницы стоит восьмой части сайта. В форме такого флага нет
намеренно — она делает сайты, а не проверяет их.

Ключ OpenAI лежит в том же `.env`, что и ключ Runware. Цену OpenAI в ответе не присылает, поэтому
фабрика считает её из счётчиков токенов и цен в `.env` — сменили `OPENAI_MODEL`, поменяйте и три
`OPENAI_PRICE_*`, иначе лог будет врать. Подробности — в
`docs/specs/2026-09-17-text-generation-design.md`.

## Промпты

Как складывается каждый запрос к моделям — что лежит в неизменяемой части, что в изменяемой, какие

## Как это устроено

Три слоя с жёсткими границами:

- `factory/` — Express-сервер и интерфейс. Знает про папки и команды, не знает про вёрстку.
- `src/` — движок на Astro. Чистая функция «контент + шаблон + схема → папка сайта».
- `templates/<id>/` — шаблоны-плагины: `manifest.json`, `.astro`-компоненты блоков и, для
  генерации текстов, `pictures.json` и папка `examples/`. Сейчас в комплекте один шаблон —
  `template1`, и одна схема — `dark`.

### Добавить шаблон

Положить папку `templates/<новый-id>/` с `manifest.json` и файлами блоков — по одному на
тип из `blocks`, имя файла совпадает с типом. Интерфейс подхватит шаблон сам;
править код движка не нужно.

Этого хватает, чтобы собрать сайт из готового контента. Чтобы шаблон умел ещё и генерацию
текстов, рядом нужны `pictures.json` — где стоит картинка и сколько ссылок можно — и папка
`examples/` с примерами страниц, по папке на адрес. Без них сборка работает, а генерация текстов
шаблон отвергнет, назвав недостающий файл.

### Добавить пример

`npm run import:sheet -- <книга.xlsx или ссылка> --example <тема>/<имя>`. Больше ничего делать не
нужно.

Папки страниц, которые при этом появятся, и есть будущие страницы сайта: прислали книгу на десять
листов — у сайта станет десять страниц. Список примеров в форме собирается из тех имён, которые есть
у **всех** страниц темы: сайт строится из одного источника целиком, и предлагать имя, которого у
какой-то страницы нет, значило бы предлагать выбор, который не сработает.

### Добавить цветовую схему

Положить `styles/schemes/<имя>.css` с тем же набором `:root`-переменных, что и в
`dark.css`. Тест проверяет, что наборы совпадают: схема без одной переменной не
роняет сборку, она молча рисует пустоту.

Схема задаёт не только цвета: градиент заголовка (`--heading-gradient`) и силу
свечения (`--accent-glow`, `--section-glow`) тоже берутся из неё.

### Контент

Сайт — это папка `data/sites/<сайт>/`: по одному JSON-файлу на страницу (адрес страницы —
имя файла, `home.json` — главная) и два необязательных служебных файла: `site.json` с общими
настройками (домен, бренд, меню, футер) и `images.json` со списком картинок. Файлы картинок —
в `data/sites/<сайт>/public/`. Подробности формата — в `docs/content-format.md`.

Валидации нет: недостающие поля получают значения по умолчанию, а всё, что не удалось вывести,
перечисляется предупреждением в логе. Сборка не падает из-за контента — падает только от
нечитаемого/не-JSON файла или от папки вовсе без страниц.
